01 — Event Processing Pipeline

Six steps between an event and its proof.

Append-only, cryptographically bound event logging. Each receipt links to the tip of the chain before it — so history cannot be rewritten without breaking every link after it.

/ 01

Check kid is live

The key ID (kid) is resolved against the live key directory before anything is signed. Revoked or unknown keys never enter the log.

/ 02

SHA-256 the payload

The canonical event payload is hashed with SHA-256, producing the payload_hash that anchors everything downstream.

/ 03

Append into Sparse Merkle tree

The leaf is inserted into a Sparse Merkle tree; the updated smt_root commits to the full set of events ever recorded.

/ 04

Bind to last tip

The new leaf is bound to the previous chain tip, yielding the new chain_root — an append-only hash chain over the entire sequence.

/ 05

ML-DSA-65 sign the leaf

The bound leaf is signed with ML-DSA-65, a post-quantum signature scheme — the receipt stays verifiable even against future adversaries.

/ 06

Write one JSONL line

The finished receipt is emitted as a single JSONL line. One line per event, one file per stream — trivial to store, ship, and audit.

02 — In Motion

Watch a receipt come into being.

One event, ten seconds: the key checks live, the payload hashes, the Merkle tree updates, the chain binds, the leaf signs — and one JSONL line lands in the log.

03 — Receipt Specification

Nine fields. Nothing to trust but math.

Every GoldTrac receipt carries exactly nine fields — the key ID, the signature, both cryptographic roots, timestamp authority information, and the application that emitted it. The full machine-readable contract lives in schema.json.

kid · string · didKey identifier

Key identifier of the signing key. Resolved for liveness at signing time.

seq · integerSequence

Monotonic sequence number of the event within its stream.

ts · string · rfc3339Timestamp

Event timestamp, attested by the timestamp authority.

payload_hash · hex · sha-256Payload hash

SHA-256 digest of the canonical event payload.

chain_root · hex · sha-256Chain root

Tip of the append-only hash chain after binding this event.

smt_root · hex · sha-256Merkle root

Sparse Merkle tree root after the leaf insertion.

sig · base64 · ml-dsa-65Signature

Post-quantum signature over the bound leaf.

tsa · objectTimestamp authority

Issuer, serial, and attestation reference.

app · stringApplication

Application that emitted the event, e.g. an integration below.

05 — Zero-Trust MPC Layer

The signing key never exists in one place.

GoldTrac's key custody is a zero-trust multi-party computation layer: every signing key is split into fragments held by independent nodes. Credentials and transaction authorizations are computed jointly — the key is never assembled in one vulnerable spot, so no single node, host, or operator can sign alone.

Honest by design

Software custody, stated plainly.

GoldTrac keys live in software custody — not in a FIPS 140-3-validated hardware module. That is a deliberate, documented trade-off: simpler deployment and portable keys, in exchange for a different key-protection boundary.

We would rather you know exactly where the boundary is than hide it behind compliance vocabulary. If your threat model requires validated hardware custody, GoldTrac in its current form is not the right fit.

  • Custody — Software-held signing keys, split as fragments across independent MPC nodes; no HSM in the current implementation.
  • Signatures — ML-DSA-65 — post-quantum, NIST-standardized.
  • Hashing — SHA-256 over canonical payloads, chain, and Merkle nodes.
  • Log model — Append-only JSONL; verification is fully offline-capable.
